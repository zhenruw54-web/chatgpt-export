# V0.2 One-time Index Migration (Edge, Windows)

**State:** Development-only instructions. No real Windows migration has been completed.
**Privacy:** Keep both small JSON files locally. Never commit or paste their contents
into a public GitHub issue, PR or ChatGPT chat. Do not paste cookies or session tokens.

## Why a one-time migration is unavoidable

The original Edge store extension and the unpacked V0.2 test extension have
different extension IDs and therefore separate `chrome.storage.local` data.
The upstream historical export index uses account/conversation keys and a
SHA-256 metadata fingerprint, not a simple list of conversation IDs.

Our V0.1 immutable baseline contains **65 unique historical conversations**.
A migrated index is safe to use only after all 65 conversation IDs are covered.
Importing an empty index would trigger an expensive full-history export.

## Small file 1: original extension's index

Use the **original installed extension's** background/service-worker DevTools
console, not the V0.2 extension console and not a normal website console.
In Edge, open `edge://extensions`, enable developer mode, locate the original
"ChatGPT Markdown Export", and open its service-worker Inspect link.
If the service worker is inactive, first open the original extension popup.

Run the following in the original extension service-worker console:

```js
chrome.storage.local.get(["cgx-export-index", "cgx-last-full-export"]).then(data => {
  const payload = {
    schema: "cgx-index-transfer-v1",
    index: data["cgx-export-index"],
    last_full_export: data["cgx-last-full-export"]
  };
  console.log("Index entries:", Object.keys(payload.index || {}).length);
  console.log("Full-export timestamp present:", !!payload.last_full_export);
  copy(JSON.stringify(payload));
});
```

Copy the clipboard **locally** to a UTF-8 file, for example
`cgx-index-transfer.json`. If `copy()` is unsupported in that DevTools
context, use the console's Copy object command (do not print or share the entire
payload in screenshots). Never edit the index fingerprints.

Expected: at least 65 index entries, each with a SHA-256 fingerprint. This is
a starting check, **not sufficient** on its own to approve migration.

## Small file 2: V0.1 verified historical IDs

A read-only helper is now available in the development branch:
`tools/export_v01_baseline_ids.py` (Python standard library only).

It checks `meta.baseline_conversation_count = 65` and reads exactly the
`versions.kind='baseline'` records. It refuses to include later synthetic
new/modified records, overwrite an existing output, or open the SQLite
database for writing. The table names were inspected from an accessible
**V0.1 test ZIP**; the real frozen SQLite database must still pass the
helper's schema and count checks.

Using an existing Python interpreter (do **not** assume the `py` launcher
exists), Work can execute, replacing both paths with the actual
verified local database and new output paths:

```powershell
python tools/export_v01_baseline_ids.py --db "C:\\path\\to\\real-v01.sqlite3" --out "C:\\path\\to\\cgx-v01-baseline.json"
```

If `python` is unavailable, find the existing installed Python executable
before installing anything. The helper must report PASS; if it reports FAILED,
do not fabricate IDs, import an unverified file, or change the database.

The output is a local UTF-8 JSON file with this shape:

```json
{
  "schema": "cgx-v01-baseline-v1",
  "conversation_ids": ["real-ID-1", "real-ID-2"]
}
```

The snippet shows the format only. It is **not** a valid baseline file;
the real file must contain exactly 65 distinct IDs from the frozen real data.
If the V0.1 records cannot be verified, stop instead of inventing missing IDs.

The tool compares conversation IDs irrespective of the account-prefix portion
of the original extension's key. This is intended to cover workspace aliases,
while preserving the imported index key and fingerprint unchanged.

## Small file 3: two verified shared alias mappings

The target extension preserves **all 65 old index keys and original
fingerprints unchanged**. It does not replace a backing ID with a
conversation ID. Instead, a receipt records exactly two proven
backing-ID-to-conversation-ID aliases, which are checked again on every
scheduler activation.

Using local Work with the original ZIPs and the already verified audit
evidence, prepare a *new* small UTF-8 JSON
\`cgx-v02-shared-alias-proof.json\` with this exact schema:

\`\`\`json
{
  "schema": "cgx-v02-shared-alias-proof-v1",
  "mappings": [
    {
      "raw": {
        "conversation_id": "REAL_CONVERSATION_ID",
        "backing_conversation_id": "REAL_BACKING_ID",
        "workspace_id": "REAL_WORKSPACE_ID"
      },
      "metadata": {
        "conversation_id": "REAL_CONVERSATION_ID",
        "workspace_id": "REAL_WORKSPACE_ID"
      },
      "index": {
        "key": "REAL_OLD_INDEX_KEY_WITH_WORKSPACE_PREFIX",
        "workspace_id": "REAL_WORKSPACE_ID",
        "fingerprint": "EXACT_ORIGINAL_INDEX_FINGERPRINT",
        "updated_at": "EXACT_ORIGINAL_INDEX_UPDATED_AT"
      },
      "raw_sha256": "SHA256_OF_ORIGINAL_RAW_JSON",
      "metadata_sha256": "SHA256_OF_ORIGINAL_METADATA_JSON"
    }
  ]
}
\`\`\`

The example shows ONE mapping's field structure only; the real file MUST
contain precisely **TWO unique mappings**. Never use literal placeholder
strings, fabricate a hash, invent timestamps, guess workspace IDs or change
the original index.

Before writing the proof, Work must independently recheck each source file's
SHA-256 against the unchanged ZIP; the extension itself cannot re-hash
unprovided original ZIP files. A 64-character hash string in this JSON is
NOT independent cryptographic proof of the original source contents. Do not
substitute self-reported proof for the local evidence audit.

The extension checks all required relationships:
- 63 direct unique V0.1 conversation IDs;
- exactly two remaining baseline IDs and exactly two old-index extras;
- each raw.conversation_id equals metadata.conversation_id and a missing ID;
- each raw.backing_conversation_id equals the old index key suffix;
- raw, metadata and index workspace IDs all match;
- original index fingerprint and timestamp match the proof exactly;
- both mappings are one-to-one, with no duplicate targets or reused keys.

A conflicting, incomplete, stale, malformed or swapped proof is rejected
before any data is written. After import, a receipt contains ONLY the two
approved key-to-ID aliases and the complete 65-ID baseline coverage check.

## Import into V0.2

1. Keep the original Edge extension and all five ZIPs untouched.
2. First confirm the **repaired six-test suite** passed on Windows and that
   Work has prepared three authentic local JSON files.
3. Install the **separate unpacked V0.2 test extension only after code review
   and explicit Windows test instructions are provided**.
4. Open the V0.2 popup → **一次性迁移旧扩展索引（本地操作）**.
5. Select the *old index*, *frozen V0.1 baseline* and *two shared mappings*
   JSON files; click the one-time import button.
6. Require 65 total baseline IDs, 2 matched shared aliases, unmodified
   65 old index entries and successful receipt readback.
7. **Do not enable the daily timer yet.** Verify a controlled new/changed
   conversation is exported correctly and V0.1 accepts the resulting ZIP.

### Hard rejection conditions

- Any source schema is invalid; fingerprint is not 64-hex; account key invalid.
- V0.1 baseline is not exactly 65 unique real historical conversation IDs.
- Direct matching is not 65/65 with no proof, or exactly 63/65 with precisely
  two independently verified shared mappings.
- Old index contains any additional unexplained keys or ambiguous aliases.
- Any proof raw, metadata, workspace, backing ID, fingerprint or timestamp
  contradicts original verified records.
- Target already has an index or a receipt; never silently overwrite.
- Scheduler is enabled/running at import time.
- Request payload exceeds 512KB, or requester is not the extension popup.
- Source last-full-export timestamp is missing/implausible.


## Rollback and security

This migration writes only the **new test extension's** local storage.
It does not delete, edit, or read the original extension's storage.
If validation fails, the target remains unchanged. Do not uninstall the original
extension, delete original ZIPs, or change V0.1 / R22 / Obsidian.

The receipt stores a local copy of the verified **65 IDs** and the two
validated shared alias keys; subsequent scheduler starts check that each ID
is still directly present or has its original verified old-index alias.
If any alias disappears, the scheduler fails closed instead of re-downloading
full history.
No raw chat messages, pictures, attachments, or authentication data should be
included in the index-transfer JSON or baseline-ID JSON.

Passing this step verifies **ID coverage and record structure only**. It
doesn't guarantee that all 65 conversation contents or media were exported,
that the old extension's fingerprints reflect every edit, or that future ZIP
downloads have landed safely on Windows. Those checks remain separate.
