# V0.2 One-time Index Migration (Edge, Windows)

**State:** Development-only instructions. No real Windows migration has been completed.
**Privacy:** Keep both small JSON files locally. Never commit or paste their contents
into a public GitHub issue, PR or ChatGPT chat. Do not paste cookies or session tokens.

## Why a one-time migration is unavoidable

The original Edge store extension and the unpacked V0.2 test extension have
different extension IDs and therefore separate `chrome.storage.local` data.
The upstream historical export index uses account/conversation keys and a
SHA-256 metadata fingerprint, not a simple list of conversation IDs.

Our V0.1 immutable baseline contains **65 unique historical conversations**.
A migrated index is safe to use only after all 65 conversation IDs are covered.
Importing an empty index would trigger an expensive full-history export.

## Small file 1: original extension's index

Use the **original installed extension's** background/service-worker DevTools
console, not the V0.2 extension console and not a normal website console.
In Edge, open `edge://extensions`, enable developer mode, locate the original
"ChatGPT Markdown Export", and open its service-worker Inspect link.
If the service worker is inactive, first open the original extension popup.

Run the following in the original extension service-worker console:

```js
chrome.storage.local.get(["cgx-export-index", "cgx-last-full-export"]).then(data => {
  const payload = {
    schema: "cgx-index-transfer-v1",
    index: data["cgx-export-index"],
    last_full_export: data["cgx-last-full-export"]
  };
  console.log("Index entries:", Object.keys(payload.index || {}).length);
  console.log("Full-export timestamp present:", !!payload.last_full_export);
  copy(JSON.stringify(payload));
});
```

Copy the clipboard **locally** to a UTF-8 file, for example
`cgx-index-transfer.json`. If `copy()` is unsupported in that DevTools
context, use the console's Copy object command (do not print or share the entire
payload in screenshots). Never edit the index fingerprints.

Expected: at least 65 index entries, each with a SHA-256 fingerprint. This is
a starting check, **not sufficient** on its own to approve migration.

## Small file 2: V0.1 verified historical IDs

Read the frozen V0.1 SQLite database in **read-only mode** or its validated
manifest/report, not the isolated 66-conversation synthetic increment test.
Inspect the actual schema rather than assuming table or column names.
Export exactly 65 **distinct** real conversation IDs to a local UTF-8 JSON
file with this shape:

```json
{
  "schema": "cgx-v01-baseline-v1",
  "conversation_ids": ["real-ID-1", "real-ID-2"]
}
```

The snippet shows the format only. It is **not** a valid baseline file;
the real file must contain exactly 65 distinct IDs from the frozen real data.
If the V0.1 records cannot be verified, stop instead of inventing missing IDs.

The tool compares conversation IDs irrespective of the account-prefix portion
of the original extension's key. This is intended to cover workspace aliases,
while preserving the imported index key and fingerprint unchanged.

## Import into V0.2

1. Keep the original extension and all five ZIPs untouched.
2. Install the **separate, unpacked V0.2 test extension only after code review
   and Edge acceptance instructions are provided**.
3. Open its existing popup → **一次性迁移旧扩展索引（本地操作）**.
4. Select the two JSON files and click **核对65条并迁移**.
5. Check that the popup reports 65 matched baseline IDs, imported index
   count, and successful readback.
6. **Do not enable the timer yet.** First test a controlled new/changed
   conversation and check the resulting ZIP is accepted by V0.1.

### Hard rejection conditions

- Neither file has the required schema marker.
- The original index contains fewer than 65 entries.
- Fingerprints are not 64-character hex SHA-256 strings.
- Duplicate/invalid V0.1 conversation IDs.
- Any V0.1 conversation ID is missing from the original extension index.
- Source full-export timestamp is missing or implausible.
- Target already has an index or receipt (never silently overwrite).
- Scheduler is enabled or running at import time.
- Transfer payload is over 512 KB.
- The request did not originate in the extension's popup.

## Rollback and security

This migration writes only the **new test extension's** local storage.
It does not delete, edit, or read the original extension's storage.
If validation fails, the target remains unchanged. Do not uninstall the original
extension, delete original ZIPs, or change V0.1 / R22 / Obsidian.

The receipt stores a local copy of the verified **65 IDs**, so subsequent
scheduler starts can recheck that all those IDs still exist in the index.
No raw chat messages, pictures, attachments, or authentication data should be
included in the index-transfer JSON or baseline-ID JSON.

Passing this step verifies **ID coverage and record structure only**. It
doesn't guarantee that all 65 conversation contents or media were exported,
that the old extension's fingerprints reflect every edit, or that future ZIP
downloads have landed safely on Windows. Those checks remain separate.
