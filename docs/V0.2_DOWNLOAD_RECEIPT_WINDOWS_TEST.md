## One problem, one fix

Previously \`exportAll()\` started an anchor ZIP download, then wrote
\`cgx-export-index\` immediately. A blocked, cancelled, incomplete or missing
download could therefore result in lost future increments.

The V0.2 scheduled export now:

1. Checks the original 65-item migrated index + 2 shared aliases before work.
2. Runs a read-only metadata preview. Rejects >10 changed items.
3. Repeats the 10-item cap inside \`exportAll()\` after its independent scan
   (prevents a race between preview and export).
4. Builds the same ZIP and embedded checksums as before.
5. Registers each ZIP blob URL with the extension background **before**
   clicking the normal HTML anchor. This preserves the existing ZIP generator
   and avoids base64 expansion of potentially large image attachments.
6. Observes only the exact blob URL's \`chrome.downloads.onCreated\` and
   \`chrome.downloads.onChanged\` events. The downloaded file must report
   \`state=complete\` and match the original in-memory ZIP size if known.
7. Waits for browser confirmation for **every ZIP part** before committing
   the updated incremental index. \`interrupted\`, wrong URL, wrong bytes,
   missing event, worker reset or timeout refuses to advance the index.
8. Refuses to advance the index on **any conversation/image/file failure**
   even if a partially complete ZIP was downloaded. A later human inspection
   is required to avoid silent loss.

The manual \`exportCurrent\` and \`cgx-export-all\` paths remain unchanged:
this receipt logic only applies to \`opts.v02Scheduled\`.

The background has access to \`downloads\` permission in the new 0.6.59.3
manifest. It does **not** request \`downloads.open\`, \`downloads.ui\` or broad
new host access, delete files, or overwrite downloads.

## Exact acceptance terminology

- **BROWSER COMPLETE**: Edge reports a finished file and matching bytes.
- **ZIP VALID**: independent Windows check finds the expected ZIP,
  verifies CRC / checksums / \`manifest.json\` and nonempty contents.
- **V0.1 ACCEPTED**: a copy of V0.1 in a safe test area reads and classifies
  the ZIP successfully, with no changes to its frozen original baseline.
- **R22 / F-DRIVE ARCHIVED**: the local R22 processing chain writes to the
  intended \`04_工作与项目/_待审核\` location and is separately verified.

The changes in this commit prove none of the last three stages. Even
\`browser_download_complete_v01_unverified\` is only the first condition.

## Remaining reliability gap

In the current code, the index commits after browser download completion,
**before** a V0.1 durable ingestion receipt. Until an explicit V0.1
acknowledgement is available, an externally deleted/corrupt file could still
leave an index entry considered processed. This is a **known remaining
blocker for production unattended archiving**, not an accepted PASS.
